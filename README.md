# 小朋友下樓梯（stair-kids）

一直往下跑的經典下樓梯遊戲。只有左右兩個方向，沒有跳；畫面上緣的天花板會越玩越快地追下來，
下得越深分數越高。**目前進度：M1（四段 AI ＋ 跟電腦對戰）。**

規格唯一來源是 [`規劃書.md`](規劃書.md)，本檔只寫「怎麼跑起來」與「M0 做了什麼」。

---

## 怎麼玩起來

**最簡單**：雙擊 `啟動遊戲.bat`（會自己找 Node，開好瀏覽器）。

**用命令列**：

```
npm start
```

然後開 <http://localhost:3060>。

**完全不裝 Node 也可以**：M0 只有單機，直接用瀏覽器打開 `public/index.html` 就能玩
（伺服器只負責發靜態檔案與 `/health`，線上模式要到 M2 才接上）。

埠號固定 **3060**（3000／3010／3020／3030／3040／3050／3090 已被 `C:\Eric\AI Agent` 底下其他遊戲佔用）。
要改就設環境變數 `PORT`，或抄 `.env.example` 成 `.env`。

## 怎麼驗

```
npm run verify         # 下面全部跑一次（零依賴、不需要瀏覽器）
npm test               # tests/verify.js           規則核心單元測試
npm run test:stairs    # scripts/stairs-check.js   一萬層樓梯：可達性、無死路、空隙看得出來
npm run test:match     # scripts/match-check.js    單機與對戰一局跑完、難度差異
npm run test:ai        # scripts/ai-check.js       四段 AI 的行為差異（各 200 局）
npm run test:online    # scripts/online-check.js   房間、席位、觀戰、搶位、邀請、斷線判輸
npm run test:online-ui # scripts/online-ui-check.js  結算快照重複抵達不會重開對局
npm run test:netcode   # scripts/netcode-check.js  假網路＋假時鐘的預測校正（可指定延遲）
npm run test:result    # scripts/result-check.js   結算內容與本機紀錄
npm run test:render    # scripts/render-check.js   死亡與結算之後的畫面清理
npm run test:audio     # scripts/audio-check.js    音訊設定
npm run test:online-chat # scripts/online-chat-check.js  對局中的文字聊天
npm run test:flow      # scripts/flow-check.js     線上完整流程（假瀏覽器跑真的 app.js）
npm run test:smooth    # scripts/smooth-check.js   線上畫面順暢度（60/144/30Hz、掉幀、延遲抖動）
```

全部都是零依賴的純 Node，不需要瀏覽器。指定延遲的用法：

```
node scripts/netcode-check.js --lag=80                      # M2 的驗收條件
node scripts/netcode-check.js --lag=200 --jitter=40 --loss=0.05
```

另外還有一支**需要另外裝 Playwright** 的端對端驗收（故意不算專案依賴）：

```
npm i -D playwright && npx playwright install chromium
node server.js                                              # 另一個視窗
npm run test:e2e                                            # 三到五個瀏覽器連同一台伺服器
```

## M0 做完了什麼

- **規則核心** `public/js/rules.js`：純函式、無 DOM、無 socket、無計時器。
  左右移動與重力、掃掠落地、五種階梯、鏡頭跟最深存活者（有追隨速度上限）＋隨時間加快的保底下捲、
  天花板把人往下推並扣血、掉出畫面下緣摔死、血量與深度計分、每 100 公尺換世界、四段難度、
  角色朝向（左／右／正面）、勝負判定（含對戰與線上的分支）、
  玩家推擠 `resolvePush`（M1 才用得到，但介面與測試先做好）。
- **樓梯生成** `public/js/stairs.js`：可注入種子、無限往下、**可達性保證**、
  連續同款上限、每 4 層保底安全落點、每 12 層喘息階、彈簧不接在刺階正下方。
- **單機一人挑戰**：首頁三顆大按鈕 → 選角色與難度 → 倒數 2 秒 → 玩 → 結算（含「這局統計」）→ 再玩一次。
- **美術**：8 隻小朋友與六套世界主題，**全部手繪向量 SVG，沒有任何 emoji 文字美術**。
  角色是頭＋身體＋雙手＋雙腳＋漸層，六組姿勢（站／走／下墜／彈起／踩刺／被頂／暈眩）。
- **音訊**：木琴童謠風 BGM，六個世界換樂器變奏，速度倍率越高節拍越快；十種音效。
  BGM 與音效音量獨立，首次手勢後才解鎖。
- **設定彈窗**：BGM／音效（各自開關＋音量）、震動、減少動態、色彩輔助、深度輔助線、
  清除本機紀錄、恢復預設。焦點鎖定、Esc 關閉、重進保留。
- **本機紀錄** `localStorage`：各難度最深深度與日期、最深世界、常用角色、上次的暱稱與角色。
- **RWD**：桌機寬版／平板直橫／手機直橫都驗過，資訊欄在左邊且刻意小，直向壓成上方薄狀態列。
- **伺服器** `server.js`：零依賴，靜態檔案 ＋ `/health` ＋ `/api/presence` ＋ 自寫 WebSocket（`lib/ws.js`）
  的最小端點，M2 才接上房間迴圈。

## M1 做完了什麼

- **四段 AI** `public/js/ai.js`：只輸出 `{ dir: -1 | 0 | 1 }`，跟真人走同一個輸入管道，不作弊
  （只看得到已經生成的階梯，還會依難度砍成「預看 N 層」；不加速、不改血量）。
  反應延遲、預看層數、避刺／避假階、彈簧的用法、挑寬階、推人、失誤率都依難度分四段。
- **跟電腦對戰**：同一座樓梯、會互相推擠、倒數 3 秒、玩家一死就結束（不必等電腦死）。
  難度由玩家挑一個，電腦用同一個（規劃書 §1.7）；**幼幼班不開放對戰**。
  資訊欄多一區對手的深度與血量（只給數字，不顯示領先／落後差距）。
  結算改成勝負標題＋勝方大頭貼＋兩行數據，統計多了「被推開」與「對手最深」。
- **`scripts/ai-check.js`**：四段 AI 各跑 200 局（8 秒跑完），驗平均深度單調遞增、
  差距大於雜訊、死亡率遞減、落地的階梯裡刺的比例遞減、不作弊、同 seed 可重現。

### 四段 AI 的實測差異（各 200 局、每局上限 90 秒）

| 遊戲難度 | AI | 平均深度 | 平均下降速度 | 死亡率 | 落地裡的刺 |
|---|---|---|---|---|---|
| 普通 | 幼幼班 | 120.7 m | 3.63 m/秒 | 90.0% | 7.3% |
| 普通 | 簡單 | 223.0 m | 3.57 m/秒 | 47.5% | 7.1% |
| 普通 | 普通 | 294.9 m | 3.51 m/秒 | 10.5% | 6.5% |
| 普通 | 困難 | 318.0 m | 3.68 m/秒 | 7.0% | 6.5% |

有兩件事要記著（`ai-check` 的註解裡也寫了）：

1. **只要 AI 好到不會死，深度就被「保底下捲速度」綁住** —— 鏡頭一直往下捲，
   玩家再快也只是跟著走。所以普通與困難這一對在高難度會收斂到同一個數字，
   真正的差別在下降速度與死亡率。這不是 bug，是這款遊戲的節奏本來就由下捲速度決定。
2. **「會不會避刺」只能看「落地的階梯裡有幾成是刺」**。用「每局幾次」或「每 100 公尺幾次」
   都會得到相反的結論 —— 強的 AI 落地次數多很多（150 次／局 對 32 次／局）。

**M2 之後（線上、觀戰、聊天）還沒做**，但規則核心已經留好共用介面：
`createMatch / stepMatch / makeStairs / resolveLanding / resolvePush / applyCeiling / checkResult`，
AI 與線上都只要送 `{ dir: -1 | 0 | 1 }` 這種和真人一模一樣的輸入。

## 待 Eric 確認的幾件事

規劃書裡有幾處內部不一致或沒寫到的地方。M0 先照下面的做法實作，**每一項都是一行常數就能改**，
不同意就說一聲。

### 1. 彈簧強度：「彈回上一層半」和「9 格／秒」互相矛盾（重要）

- §0.1 決策表寫 **「溫和：彈回上一層半」**，§1.3 參數表寫 **「向上彈初速 9 格／秒」**。
- 但 9 格／秒 在重力 30 格／秒² 下只彈得起 `9² / (2×30) = 1.35 格`，
  而層間距是 2.0～3.0 格 —— 換算下來大約只有 **半層**，不是一層半。
- 要真的彈回一層半（3.0～4.5 格）需要 **約 15 格／秒**。
- **M0 先照 §1.3 的具體數字實作 9 格／秒**（比較溫和、比較安全）。
  要改成一層半就把 `public/js/rules.js` 的 `C.SPRING_VY` 從 `9.0` 改成 `15.0`
  （`tests/verify.js` 是用公式驗的，改了數字測試照樣會過）。

### 2. 輸送帶與彈簧的出現比例，規劃書沒給

§1.7 的難度表只給了刺階與假階的比例。M0 先假設 **輸送帶 14%、彈簧 10%，四段難度都一樣**
（只有刺階與假階跟著難度變），在 `public/js/stairs.js` 的 `C.BELT_RATE` / `C.SPRING_RATE`。
實測一萬層的實際比例（連續性限制會壓低一點）：

| 難度 | 普通 | 輸送帶 | 彈簧 | 刺 | 假 |
|---|---|---|---|---|---|
| 幼幼班 | 78.6% | 12.3% | 9.1% | 0% | 0% |
| 簡單 | 63.9% | 13.1% | 8.5% | 6.9% | 7.6% |
| 普通 | 55.4% | 12.9% | 8.2% | 11.1% | 12.5% |
| 困難 | 48.6% | 13.1% | 7.9% | 15.1% | 15.3% |

### 3. 可達性算式裡的「水平距離」沒有定義

§3 寫「新階與上一層的水平距離不得超過 落下時間 × 6 格／秒 × 0.8」，但沒說是中心距還是邊緣距。
M0 採用 **兩階水平區間的邊緣距離（重疊算 0）**，理由是玩家站在上一階時就能先走到靠近的那一端，
這才是物理上真正要跨越的距離。

同時多做了一件規劃書沒寫、但不做會有死路的事：**新階必須從「上一層的每一階」都走得到**，
不是只從其中一階。因為上一層偶爾會有兩階，玩家可能站在任何一階上。
這條連帶推出「同一層兩階最遠只能隔 6.0 格」（`C.TWO_STEP_MAX_SEP`，推導寫在程式註解裡）。
`scripts/stairs-check.js` 會用貪心模擬走完一萬層，四段難度目前都是 **零死路**。

### 4. 輸送帶「順向」的速度規劃書沒寫

§0.1 只給了逆向的 `6 − 3 = 3 格／秒`。M0 採用相加：**順向 6 + 3 = 9 格／秒**。

### 5. 天花板扣血間隔比刺階無敵時間還短

困難難度是每 0.4 秒扣 1 顆，但踩刺的無敵是 0.6 秒。
依 §1.5「期間不再受**同類**傷害」，M0 把兩種傷害分成各自獨立的計時：
踩刺有 0.6 秒無敵、天花板照自己的間隔扣，互不影響。

### 6. ~~被天花板頂住時會不會被壓穿階梯~~（已定案，並改掉了三條決策）

Eric 後來指定：**被天花板頂到要自動被往下推**，而且**掉出畫面外要直接墜落死亡**。
這兩件事合起來是一套一致的設計，但會動到 §0.1 決策表的三條，已經照著改完：

| 原本的決定 | 改成 |
|---|---|
| 鏡頭跟最深存活者（瞬間跟上） | 鏡頭跟最深存活者，但**有最高追隨速度 8 格／秒**（`C.CAMERA_CATCHUP`） |
| 唯一的死法是血歸零 | 再加一種：**掉出畫面下緣直接淘汰**（結算標成「摔下去了」） |
| 被頂住持續扣血（站著被夾住） | 被頂到**推穿腳下的階梯往下掉**；**碰到刺就立刻扣 1 顆**，之後等冷卻（原本的間隔變成冷卻時間） |

- 為什麼鏡頭要加上限：原本鏡頭瞬間跟上，玩家永遠被鎖在離上緣 12 格的位置，
  實測連續踩空 20 秒、掉了 355 公尺都還在畫面正中間，**根本掉不出去**。
  加上限之後，自由落體最快 18 格／秒、鏡頭最快 8 格／秒，追不上的那 10 格／秒
  就是你往下沉的速度。實測**連續踩空約 16 格（5～6 層）就會摔死**。
- 為什麼扣血要改成「碰到就扣」：天花板會把人推穿階梯，所以接觸永遠是斷斷續續的
  （實測平均一次 0.15 秒、最長 0.4 秒）。要求「連續」接觸滿一個間隔的話就永遠扣不到血，
  §0.1 的「被上方天花板刺頂住持續扣血」等於被刪掉 —— 原地不動 40 秒只掉 4 顆血還死不了。
  §1.7 的間隔（0.9／0.6／0.4 秒）改成解讀為「冷卻時間」：碰到刺當下就扣 1 顆，
  冷卻結束前再碰不會重複扣。實測原地不動會在 8～33 秒內死掉（依難度），
  而且第一顆血在 2.9～5.2 秒就掉了，玩家看得到因果關係。
- **幼幼班例外**：鏡頭沒有追隨上限（永遠追得上），所以沉不出畫面、不會摔死，
  維持 §0.2 的「鼓勵式不死」。
- **附帶影響**：§7.1 原本說手機橫向要「縮短可見高度到 14 格並放大角色」，
  但摔死的判定線就在 18 格，看不到判定線會死得莫名其妙，所以手機橫向也改成一律顯示 18 格。
  要改回去是 `app.js` 的 `applyRenderOptions()` 一行。

### 7. 幼幼班的 20 顆愛心其實一滴都不會掉

幼幼班不出刺階、不出假階、天花板也不扣血，所以血量純粹是裝飾。
M0 照決策表照做（顯示成「愛心 × 20」），只是提醒一下這是必然結果。

### 8. `makeStairs` 放在哪一支

§9 的檔案結構把樓梯生成放 `stairs.js`，§4.3 又把 `makeStairs` 列在 `rules.js` 的介面裡。
M0 的做法：實作在 `stairs.js`，`rules.js` 直接轉出 `Rules.makeStairs`，兩邊都叫得到。

## 依實測回報改掉的規則（都在 §0 決策表之外或與之衝突，已記在這裡）

| 你回報的 | 原本 | 現在 |
|---|---|---|
| **「下不去」** | 被天花板頂到就是死亡螺旋：位置每一格被夾回 `cameraTop + 1.6`，只能跟著鏡頭走，**每踩一階掉 1 顆血、8 秒內必死**，玩家完全沒有自主權 | 被頂到會拿到 **14 格／秒的向下初速**（`C.CEIL_PUSH`），下一格就脫離接觸 |
| 踩到彈簧碰到天花板會一直在上面跳 | 彈簧給 −9（往上），天花板只夾位置不管速度 → 無限彈跳到死 | 同一個向下初速會抵銷向上的速度，撞到天花板就往下走 |
| 踩到非刺的地方要回血 | 沒有回血 | 踩到**普通／輸送帶／彈簧／假階**都回 **1 顆愛心**（`C.HEAL_ON_LAND`），刺階不回。「踩到」的當下才回，站著不會一直回 |
| 結算要在原房間呈現 | 換到 `#screen-result` 路由 | 改成蓋在樓梯畫面上的浮層（`#ov-result`），樓梯定格留在後面 —— 照 `whack-a-mole` 的「等待／準備／結算都用蓋在盤面上的浮層，不另外換路由」慣例 |
| 畫面滾動要更柔順 | 直接畫「最後跑完那一格」的狀態 | 加了**畫面內插**：每一格推進前存一份位置，畫的時候按累積器餘數插值。規則核心完全沒動 |

### 「下不去」的成因

鏡頭跟隨是「最深存活者 − 12 格」，被頂到時玩家只離上緣 1.6 格。要回到 12 格的安全位置
得比鏡頭多掉 10.4 格，但階梯每 2.5 格就接住他一次，所以永遠追不回來。
`tests/verify.js` 有這一條的回歸測試（12 秒、下方每 2.5 格都有階梯，必須還活著）。

### 內插的效果（模擬 600 個畫格量的）

| 畫面更新率 | 內插前 | 內插後 |
|---|---|---|
| 60Hz 穩定 | 抖動 0%、停格 0% | 抖動 0%、停格 0% |
| 60Hz 有抖動 | 抖動 20%、停格 2% | 抖動 7%、停格 0% |
| 75Hz | 抖動 50%、**停格 20%** | 抖動 4%、停格 0% |
| 120Hz | 抖動 100%、**停格 50%** | 抖動 4%、停格 0% |

（「停格」＝ 那一個畫格鏡頭完全沒動。120Hz 螢幕原本有一半的畫格是靜止的，這就是頓的來源。）

### 回血帶來的平衡變化（要注意）

加了回血之後，**會操作的玩家幾乎不會死**：每次落地都回血，而鏡頭又跟著你，所以根本碰不到天花板。
驗收機器人在三段難度都撐過 180 秒上限、全程滿血：

| 難度 | 180 秒的結果 | 90 秒 × 5 局平均 |
|---|---|---|
| 簡單 | 554 m，血量 12/12 | 250.8 m（2.8 m／秒） |

## M2 做完了什麼（伺服器端＋客戶端同步）

- `lib/rooms.js`：房間、2 席位、觀戰（上限 20）、搶位（先按先得）、邀請連結（可撤銷、與房間同生命）、聊天。完全不碰 socket，所以可以直接寫測試。
- `lib/match-loop.js`：固定 30Hz 權威迴圈、快照增量廣播、每秒心跳掃描。時鐘與送出動作都是注入的，所以驗收可以用假時鐘跑。
- `lib/protocol.js`：客戶端能做的每一件事。客戶端只送 `{ seq, dir, ct }`，永遠不送座標與血量。
- `public/js/net.js`：本地預測 → 收到快照覆蓋權威狀態 → 用輸入紀錄重演回「現在」→ 對手延遲 100ms 內插。
- `server.js`：從 M0 骨架換成完整房間伺服器，`/health`、`/api/presence`、`/api/rooms` 回真實數字。

### 一個關鍵修正：本地模擬必須「超前跑」

第一版的預測是「收到快照 → 蓋回來 → 重演到剛剛的本地時間」。這樣本地時鐘會被**延遲過的**快照綁住，
量到的超前量只有 16ms，於是按下方向鍵之後，下一份快照就把角色打回原位。

實測（200ms 延遲、按住右邊 100ms）：

| | 走的距離 |
|---|---|
| 理論值（6 格／秒 × 0.1 秒） | 0.60 格 |
| 修正前 | 0.20 格 |
| 修正後 | 0.60 格 |

修正方式：本地要跑到「這份快照的時間 ＋ 單向延遲 ＋ 一個 tick」，這樣按鍵送到伺服器時
剛好是它正在算的那一格。延遲突然變好時不硬拉時鐘，而是讓接下來幾格跑慢 15% 收回來。

### netcode-check 的實測數字

`node scripts/netcode-check.js --lag=<ms> [--jitter=<ms>] [--loss=<0~1>]`
（假網路、假時鐘、固定 seed，所以同一組參數每次跑出同一局）

| 延遲 | 同一時間點的預測誤差（平均 / p95） | 鏡頭誤差 | 重演步數 |
|---|---|---|---|
| 0ms | 0.12 格 / 0.5 格 | 0.006 格 | 3.7 步 |
| 80ms（M2 驗收條件） | 0.13 格 / 0.5 格 | 0.000 格 | 6.7 步 |
| 200ms ＋ 抖動 40ms ＋ 丟包 5% | 0.05 格 / 0.5 格 | 0.004 格 | 11 步 |
| 400ms ＋ 抖動 80ms | p95 掉到 0.60 格（會過門檻，但看得出來變差了） | | 22 步 |

- 誤差門檻一律寫成「角色寬度的幾成」而不是固定格數。
- 樓梯**不靠網路傳**：兩邊用同一個 seed 各自算，階梯 id 是 `L<層>-<序>`，所以完全對得上。
  只有假階的崩解狀態會變，那個才跟著快照走 —— 而且 `dirty` 是「所有正在裂或已經碎掉的
  階梯」的**完整清單**，客戶端收到就要把不在清單裡的清回原狀。只更新清單裡那幾階的話，
  本地預測先踩上的假階引信不會被回捲，而回溯重演每收一份快照就再扣一次，
  引信會以四倍速燒完（實測誤差 2.35 格，人先掉下去又被拉回階梯上）。

### 左右移動與推擠的手感

這兩件事都被實際玩到抱怨過（「往右移一格會被往左移動一點點」「推擠的時候會閃爍抖動」），
成因不同，各修一邊：

| 問題 | 成因 | 做法 |
|---|---|---|
| 改方向會被回拉 | 伺服器一個 tick（33ms）只用一個方向，封包到了就整個 tick 都用新方向，跟本地預測換方向的那一步差最多一整個 tick | 客戶端在 `input` 上帶 `at`＝「這個方向從對局時間的哪一刻開始生效」，伺服器排隊到那個子步才套用（`lib/rooms.js` 的 `inputQ`） |
| 推擠會閃爍抖動 | 對手的位置被畫面內插（刻意延遲 100ms）蓋掉，本地預測的推擠因此拿「快 180ms 前的對手」在算，跟伺服器結果不同，每份快照都把我拉回去一次 | 對手改成兩個位置：`viewX`／`viewY` 給畫面（延遲、順），`x`／`y` 給邏輯（推測、準），推擠算在推測位置上 |

實測（80ms 延遲、一直按同一邊推向對手）：單次最大回拉 **0.57 → 0.056 格**、
x 平均預測誤差 **0.055 → 0.007 格**、反向畫格 **39.7% → 6.4%**（剩下的是「真的被對手推回來」，
那是遊戲本來就該有的行為）。對手的動畫狀態翻轉也從 143 次降到 27 次 —— 這就是「閃爍」的來源之一。

**還沒做的**：伺服器只在 tick 邊界處理封包，所以約 13% 的輸入會晚一個 1/60 步才生效
（實測最遲 17ms ＝ 0.1 格）。要完全消掉得讓伺服器也能小幅回溯，成本遠大於收益。
把客戶端的超前量從 10ms 加到 35ms 試過，反而更差（預測暴露的時間變長）。

### 推擠的時候人物不能重疊

上面那個「對手有兩個位置」的做法會帶出一個新問題：物理上剛好貼著的兩個人，畫面上會疊
進去半個身體（因為對手的圖是他 100ms ＋ 本地超前量之前的位置）。實測重疊 0.65 格
＝身寬的 52%（200ms 延遲時 0.88 格），而伺服器上的間距永遠剛好是身寬。

做法：`net.js` 的 `contactWeight()` —— **越靠近就越把畫面位置拉回預測位置**，貼上去的時候
完全用預測位置。遠處保留內插的平順，近處不會重疊，中間是連續的（靠近的過程中圖自己追上來）。
權重的邊界要跟規則核心一致（`resolvePush` 是 `dy < PLAYER_H` 就會分開），而且淡出的終點
一定要等於「權重歸零」的門檻 —— 兩個數字不一致的話，權重會在門檻上從 0 跳到 0.76，
對手就在畫面上跳 0.46 格（144Hz 特別明顯）。

實測：肩並肩硬推 **0.65 → 0.000 格**（完全不重疊）。剩下「從對方旁邊掉下去」的那幾幀
還有 0.30 格 —— 對手的垂直位置是延遲值、本地預測又超前，兩邊對高度的看法可以差到一個身高，
那已經不是畫面問題而是預測極限；試過把權重也看畫面距離，重疊會歸零，但對手改為跳 0.75 格，
不划算。

### 自己被打到的反饋要即時

線上對戰被刺到時，閃光、震動、火花原本要等伺服器的快照回來才播，比「畫面上踩到刺的那一刻」
晚一個單向延遲 ＋ 一個 tick（實測 40～60ms）。

做法：本地預測跑出來的事件，**自己身上的**先播（`net.js` 的 `emitPredicted`）；伺服器那份
到了再一對一對消，所以不會播兩次。能這樣做的前提是傷害數字本來就可重現 ——
`rules.js` 的 `rollSpikeDamage()` 是拿 seed 揉雜湊算的，不吃亂數序列，所以本地算出來跟
伺服器一模一樣（連天花板的 `ceilHits` 也跟著快照同步，不然那個 tag 一旦錯開就永遠不同）。

對消的鑰匙用**事件步號**（伺服器在 `lib/rooms.js` 把 `at = round(match.time / STEP)` 蓋上去），
不能用秒數：快照的 `time` 只帶到小數三位，客戶端從那個四捨五入過的值往前跑，秒數會差幾十微秒，
永遠對不起來。

實測（0／80／200ms）：反饋比伺服器算出來早 **72～88ms**、伺服器算出來的每一次都播到、
預測錯而多播 0～1 次、傷害數字 100% 一致。

順手修掉一個一直都在的 bug：`room.pending` 是「上一個 tick 發生的事」，結算階段不再推進對局，
所以它會停在最後那一份（含最後一次受傷、淘汰），而快照每個 tick 都帶著它 ——
客戶端在結算的十秒內以 30Hz 重播死掉那一下的音效與震動（實測同一次被送了 50 次以上）。

**M2 還沒做的**：大廳與房間的畫面（`public/js/online.js` 與 UI）。伺服器端與客戶端腦袋都已經驗過了。

### 找到並修掉的心跳誤判（這個 bug 只有用真瀏覽器跑才會出現）

一局打完之後，**還開著的分頁會被判定斷線，整間房被關掉**。伺服器 log 寫得很清楚：

```
[hb] 心跳連續沒回，判定離線：p74287ed8b697, pb9c4a200e958
```

原因：原本的心跳只認應用層的 `hb` 訊息。對局中不會出事（客戶端一直在送輸入意圖，
順手就重設了計數），但**一局結束、沒人在送輸入之後**，只要瀏覽器把分頁節流一下、
或某一格畫得比較久，JS 晚幾秒才回話就會被當成斷線。單頁測試看不到，
因為要三、四個分頁同時跑才會被節流。

改成三層一起判斷：

| 層 | 做法 | 為什麼要有它 |
|---|---|---|
| 網路層 | 伺服器每秒發 WebSocket ping，`lib/ws.js` 記下最後一次收到**任何** frame 的時間 | 瀏覽器的 pong 是網路層自動回的，**不需要跑到 JS** —— 分頁被節流也照樣會回 |
| 協定層 | `lib/protocol.js` 收到**任何**訊息就重設計數 | 聊天、按準備、送輸入…有動作就代表人還在 |
| 應用層 | 原本的 `hb` 一問一答 | 保留，當作額外的確認 |

這樣分得出「連線真的斷了」與「這個分頁忙了一下」。修好之後同一份測試跑起來
**心跳誤判 0 次**（之前每一局結束都會發生）。

### 畫面順暢度驗收（`scripts/smooth-check.js`）

「對手有殘影」「站到會消失的平面上會跳動」這種問題，程式碼本身不會報錯，
只有量「每一格畫面角色在螢幕上動了多少」才抓得到。這一支用同一個假瀏覽器
（`scripts/fake-browser.js`）跑真的前端，直接讀角色圖層每一格被寫進去的
`transform`，再用角色自己的 `scale(k)` 把像素換回「格」，所以門檻可以直接
用規則核心的速度上限來算（落速 18 ＋ 鏡頭追速 8 ＝ 26 格／秒）：

| 指標 | 意思 | 修好前 → 修好後 |
| --- | --- | --- |
| 單幀最大位移 | 一格畫面移動幾格；超過物理上限就是瞬移 | 對手 0.65 → 0.13 格（144Hz） |
| 來回幅度 | 連續兩幀反向的較小邊，也就是抖動大小 | 3.49 → 0.07 格 |
| 大幅來回比例 | 反向 > 0.15 格的畫格佔比 | 67% → 0% |

跑的組合：60Hz／144Hz／30Hz 畫面 × 0ms／80ms／200ms＋40ms 抖動，
再加「伺服器權威迴圈被拖慢成 100ms 一次」與「分頁被節流成 4Hz 再回來」。
每一種都驗倒數 3、2、1 有顯示、兩個角色都畫得出來、結算只出現一次。

### 假瀏覽器跑真前端的流程驗收（`scripts/flow-check.js`）

「結算畫面殘留」「回到房間開不了下一局」這類 bug 都不在某一個函式裡，而在四層
接起來的縫上：伺服器的房間階段（`lib/rooms.js`）× 快照（`lib/match-loop.js`）
× 線上狀態機（`public/js/online.js`）× 畫面流程（`public/js/app.js`）。
單元測試量不到，所以這一支在 Node 裡放一個最小的假瀏覽器（DOM、rAF、
`setTimeout`、WebSocket、localStorage、假時鐘），照 `index.html` 的順序把
`public/js` 全部載進同一個 context，另一端接真的 rooms ＋ match-loop ＋ protocol，
對手用第二條真的協定連線。**按鈕是真的 `click()`，畫面狀態是真的從 DOM 讀出來的。**

走的流程：首頁 → 大廳 → 開房間 → 對手加入 → 兩人準備 → 開始 → 對戰 → 雙方死亡
→ 結算（再來一局／回到房間／回首頁三顆）→ 再來一局 → 回房間（按鈕跟原本開房間一樣）
→ 等對方準備好才能開始 → 第二局 → 回到房間 → 第三局 → 回首頁 → 斷線退回大廳。
它一樣是零依賴、不用瀏覽器，所以有進 `npm run verify`。

### 用真瀏覽器跑的端對端驗收

`scripts/e2e-online.js`。**故意不算專案依賴**（遊戲本身零依賴是硬規則），

## 依 Eric 回報改掉的第二批規則（間隙、角色大小、傷害、難度）

### 1. 「間隙判斷不夠明顯，以為能下去」——真的是 bug，不是手感問題

落地判定是「身體只要碰到階梯就站得住」（`rules.js` 的 `overlapsX`），所以要從一個空隙掉下去，
**整個身體都得塞進去**，空隙必須比玩家還寬。

而舊的參數是：

| | 值 | 玩家寬 | 結果 |
|---|---|---|---|
| 同一層兩階的最小間隔 | 0.9 格 | 1.0 格 | **永遠過不去**，但畫面上明明有一條縫 |
| 貼牆的細縫 | 沒有規定，可能 1.2 格 | 1.0 格 | 只剩 0.2 格餘裕（約 10px），等於在賭 |

現在的規則（`stairs.js` 的 `MIN_PASS = 2.5`）：**任何空隙要嘛 0（貼死），要嘛 ≥ 2.5 格，
中間的模糊值一律不產生。** 2.5 格是玩家寬度（1.25 格）的兩倍，餘裕一眼就看得出來。

實作上要注意：不能「抽完再吸附」——吸附會把階梯推出可達範圍，實測會生出 25 處死路。
正確做法是先把模糊帶從可抽的區間裡挖掉再抽（`clearX0()`）。四段難度各一萬層實測：
模糊細縫 0 處、死路 0 處、為了可達性放行的模糊縫 0 層。

Eric 給的另一個選項「同一個水平只能有一個東西」也留著：把 `TWO_STEP_CHANCE` 設成 0 就是。

### 2. 角色放大 ＋ 可操作寬度放寬

| | 之前 | 現在 | 為什麼 |
|---|---|---|---|
| 玩家寬 × 高 | 1.0 × 1.6 格 | 1.25 × 2.0 格 | 「這條縫我塞不塞得進去」要用眼睛就判斷得出來 |
| 可見高度 `VIEW_H` | 18 格 | 14 格 | 畫面拉近，每一格的像素變大 |
| 鏡頭領先 `CAMERA_LEAD` | 12 格 | 8.5 格 | `VIEW_H` 同時是死亡線，緩衝要一起收（維持約 0.55 秒的下沉餘裕） |
| 層間垂直間距 | 2.0～3.0 格 | 2.6～3.6 格 | 角色高 2.0 格了，太密會一直被天花板夾 |
| 階梯寬 | 2.5～4.0 格 | 2.8～4.2 格 | 跟著角色一起放大 |
| 出生平台 | 8 格 | 6 格 | 兩側各留 3 格 ＞ MIN_PASS，才不會一開場就是模糊細縫 |
| 桌機限寬 / 資訊欄 | 1180 / 300px | 1320 / 276px | 場地多拿到 164px |

近正方形視窗（940 × 903）實測：場地佔畫面寬從 **66% → 76%**，角色從 42px 寬變成 74px 寬。

`render.js` 的角色尺寸改成直接問規則核心（`Rules.C.PLAYER_W／PLAYER_H`），不再自己抄一份
`view.scale * 1.6`。SVG 本地座標是 100 × 160 ＝ 1 : 1.6，所以只要維持 `PLAYER_H = PLAYER_W × 1.6`
就可以用單一縮放，不會把小朋友壓扁。

### 3. 被刺到扣 1～5 顆（隨難度與深度）

Eric 指定：「被刺到一次損失的血量 1～5 隨機，可根據模式跟現在遊玩的程度選」，並給了 1～3 與 2～4 兩組。
照這個範圍鋪成四段（`base` 是淺處、`deep` 是第 3 個世界＝300m 之後，中間線性內插）：

| 難度 | 血量 | 淺處傷害 | 深處傷害 | 大概被刺幾次會死 |
|---|---|---|---|---|
| 幼幼班 | 20（不扣血） | — | — | 不會死 |
| 簡單 | 14 | 1～2 | 1～3 | 約 9 次 |
| 普通 | 10 | 1～3 | 2～4 | 約 5 次 |
| 困難 | 9 | 2～3 | 3～5 | 約 2～3 次 |

天花板的刺套同一組數字（那也是刺）。

**亂數必須可重現**：客戶端會回溯重演，用連續的亂數序列會被多消耗，前後端就對不起來。
所以 `rollSpikeDamage()` 不用亂數序列，而是把 `seed ＋ 玩家 ＋ 這次事件`（踩到的階梯 id、
或第幾次被天花板頂到）揉成雜湊值取餘數 —— 同一次事件算幾遍都是同一個數字。

畫面上：跳出「−3」的數字，震動強度、閃紅光強度都跟傷害成正比（`app.js` 的 `popDamage()`）。

### 4. 「難易度不太明顯」

三段對戰難度的參數全部拉開：

| | 保底下捲 | 加速 | 上限 | 血量 | 天花板扣血間隔 | 刺 / 假階比例 |
|---|---|---|---|---|---|---|
| 簡單 | 1.8（原 2.0） | 每 22 秒 +8% | ×1.8 | 14（原 12） | 1.2 秒（原 0.9） | 6% / 6% |
| 普通 | 2.8 | 每 20 秒 +12% | ×2.2 | 10 | 0.6 秒 | 15% / 14% |
| 困難 | 3.6 | 每 18 秒 +15% | ×2.6 | 9（原 8） | 0.4 秒 | 24% / 20% |

驗收機器人（`match-check` 的貪心假手）實測，5 局平均：

| | 撐多久 | 下降速度 |
|---|---|---|
| 簡單 | 90.0 秒（撐到上限） | 1.9 m／秒 |
| 普通 | 54.4 秒 | 2.9 m／秒 |
| 困難 | 21.6 秒 | 3.0 m／秒 |

順帶修掉兩個**指標本身有問題**的驗收項目（跟之前 AI 那次同一類錯誤）：

- 「同樣時間內越難掉得越深」比的是總公尺數，但那個數字被存活時間汙染了：簡單一路撐到 90 秒上限，
  公尺數自然多。改成分開驗「下降速度單調遞增」與「存活時間單調遞減」。
- 「越弱的 AI 死亡率越高」在困難難度下四段全部 100% 陣亡（這是對的，這個難度本來就該致命），
  打滿天花板就不可能單調。改成「單調不遞增，並容許兩個標準誤內的倒掛」（200 局的抽樣誤差約 3.5 個百分點）。

### 5. 順帶的平衡副作用（正面的）

之前記在「回血帶來的平衡變化」那一節的問題 —— 落地回 1 顆讓好手幾乎不死、一局收不了 —— 
被傷害改成 1～5 顆之後自然解掉了：回血 1 顆追不上平均 2～4 顆的傷害。
`ai-check` 實測，困難難度下四段 AI 全部會死（之前上面兩段是不死的）。

## 放寬遊戲畫面的比例（Eric：「再盡量放寬遊戲畫面的比例」）

| 項目 | 原本 | 現在 |
|---|---|---|
| 場地寬 `FIELD_W` | 12 格 | **16 格** |

| 死亡線以下留白 `VOID_UNITS` | — | 2.2 格（觸控直向自動收高，空出來給方向鍵） |

（原本是 76%）。四段難度各跑兩萬層樓梯，`gen.blurry` 仍然是 0 —— 加寬沒有帶進模糊細縫。

一起改掉的相依處：`tests/verify.js` 有 34 處把場地寬寫死成 `12`、出生平台中心寫死成 `6`，

**八輪（對局中打過字之後就不能操作，Eric 回報）**：症狀是「線上版其他玩家鍵盤不能操作」，
實際上是**誰打過字誰就不能動**。`input.js` 的 `typing()` 會在焦點落在輸入框時擋掉所有方向鍵
（這是對的，不然打不了字），但對局聊天送出之後焦點還留在輸入框 —— 玩家打完一句話就再也不能操作，
畫面上也完全看不出原因，只能被天花板追上。三件事：

- **送出就把鍵盤還給遊戲**（`online.js` 的 `submitChat` 多一個 `giveBack`）。
  房間的聊天室不變，那裡沒有在玩，留著焦點才好連續打字。
- **Esc 從輸入框跳回遊戲**（不用找滑鼠點畫面）。Esc 在輸入框裡不往上傳，
  所以第一下是離開輸入框、第二下才是叫出選單。
- **聚焦時把話講出來**：聊天區多一行「打字中：方向鍵停用，送出或按 Esc 回到遊戲」。
  另外 `app.js` 進遊戲畫面前一律 `blurTyping()`，房間的聊天／暱稱欄留下的焦點也不會帶進對局。

回歸驗收加在 `scripts/online-chat-check.js`（假 DOM 的焦點會發出 `focus`／`blur` 事件）：
送出後焦點離開、Esc 後焦點離開、房間聊天維持連續打字。拿掉修正這三項會紅。

**九輪（直向狀態列真的放不下、方向鍵太胖，Eric 回報）**：第七輪只把左右的 padding 讓夠，
但**溢出的 flex 內容不會替你留 padding-right** —— 放不下的那一段會直接滑到右上角的設定按鈕
底下被蓋掉。實測 390 px 的手機：單機要 253 px、線上要 314 px，位置只有 218 px。三件事：

- **放不下就照優先序收**（`app.js` 的 `fitSideBar()`）：量出狀態列的可用寬度與內容寬度，
  照 §7.1 的優先序 深度 ＞ 血量 ＞ 對手深度 ＞ 速度倍率 ＞ 世界，從最不重要的開始收。
  深度多一位數、愛心變少、換世界、對手淘汰都會重量（用簽章擋掉每一格都量）。
  `≤380 px 就把世界名稱收掉` 那條寫死的規則也拿掉了 —— 放不放得下用量的，不用猜。
- **對局中的聊天塊在直向要整塊收掉**：它有 86 px 高的訊息列表與輸入框，排進那一條 row
  會把狀態列撐成三倍高，還把深度與血量擠到按鈕底下。手機直向的對局就不聊天了
  （房間裡照樣有完整聊天室與快速短語）。
- **方向鍵壓矮、樓梯畫面長高**：直向 136×112 → 128×88、下緣 24 → 14 px，
  而 `fitStage()` 改成把樓梯畫面收到「方向鍵上緣再留 8 px」而不是收到 `wantStageH` ——
  以前兩者之間會空出一條幾十 px 的帶狀空白，那條既不是遊戲也不是操作區。
  多出來的高度全給樓梯畫面，`render.js` 的 `voidTop` 也改成**從死亡線開始畫**，
  死亡線以下就是一口越來越黑的井（以前深淵固定貼在畫布最下面，中間那段是看不出意思的空白，
  紅色下墜警示還跑到死亡線下面好幾十 px）。

## 斷線寬限：手機切出去再回來，房間還要在（Eric 回報）

症狀是「房間在有人的時候會自動關閉」。真正的情形是**手機一切到別的 App 連線就斷**——
開好房間、切去 LINE 把邀請連結貼給朋友、切回來，房間已經沒了，剛貼出去的連結也一起失效。
原因是 `closeIfEmpty()` 一發現沒人就立刻刪房，而「沒人」只要 3 秒沒心跳就成立（§14.1）。

- **斷線造成的空房留 60 秒**（`CONST.EMPTY_GRACE_MS`）：`closeIfEmpty(room, grace)` 只在
  `grace` 且還在等人階段時記下 `emptyAt`，真正的關房交給 `tick()`。邀請連結一起留著。
  自己按「離開房間」是真的要走，照舊立刻關；對局中沒人看也立刻關（沒有留的意義）。
  空房不會出現在大廳列表（`listRooms()` 本來就會濾掉沒人的房間）。
- **等人階段的斷線＝離開席位**：重新連上線一定會拿到新的 `personId`（每條連線發一個），
  舊席位永遠不會有人回來坐。留著會佔住席位、`hostId` 還掛在回不來的人身上 ——
  本人切回來只能當觀戰、開不了下一局。
- **客戶端會自己走回去**：斷線時記住房號（`S.wantRoom`），重連後自動 `join` 回同一間；
  另外掛 `visibilitychange`，畫面一回到前景就重連（`onclose` 的三次自動重試通常在背景就用完了）。
  自己離開或被踢會清掉 `S.wantRoom`，不會硬把人拉回去。

驗收：`online-check.js` 多 12 項（房間留著、邀請連結還有效、切回來坐得回席位且還是房主、
寬限過了才真的關、對局中兩個人都斷線照舊立刻關）；`flow-check.js` 的「斷線」那一段
從「退回大廳」改成「自己走回同一間房、還是房主、舊席位有收掉」。

## 放寬之後修掉的兩個驗收 bug（`match-check.js`）

放寬場地與放大角色之後，`scripts/match-check.js` 有三項失敗。兩個原因，都不是遊戲本身的問題：

1. **貪心機器人走不出階梯邊緣。** `rules.js` 的支撐判定是「腳掌還跟階梯有重疊就站得住」
   （`overlapsX`），所以要走出右緣得走到 `x1 + 人物半寬`。角色放大成 1.25 格之後半寬是 0.625，
   而機器人裡的 `OUT` 是固定值 **0.55** —— 目標點落在還踩得到的位置上，機器人就在
   `x1 + 0.55` 附近左右各 0.1 格抖了整整一秒走不出去，被天花板追上夾死
   （困難每秒下捲 3.6 格，一秒就是三層）。實測掉到 8 m 就結束。
   把 `OUT` 改成 `Rules.C.PLAYER_W / 2 + 0.1`（從人物寬度算出來）之後就正常了。
2. **存活時間的平均值被時間上限截斷。** 難度差異那一段原本上限 90 秒，簡單有 4／5 局撐到上限，
   平均被壓在 90 以下，跟普通的 80.8 秒幾乎一樣 —— 那不是難度沒差異，是尺量到底了。
   上限開到 300 秒之後：**簡單 246.0 秒（4／5 局仍到上限，所以這是下界）→ 普通 89.3 → 困難 43.2**，
   單調成立。順手多加一項「越難越少局能撐到上限（4 → 0 → 0 局／5 局）」，
   那是不受截斷影響的統計量。

現在 `npm run verify` 七套全綠：194 ＋ 81 ＋ 52 ＋ 23 ＋ 48 ＋ 62 ＋ 59＝**519 項全過**。
